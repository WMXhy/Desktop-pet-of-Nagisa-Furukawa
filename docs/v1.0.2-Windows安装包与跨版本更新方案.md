# v1.0.2 更新方案｜Windows 安装包与跨版本升级

**决定：从 v1.0.2 起，Windows x64 每版向玩家提供一个完整的 `Setup.exe`。** 新玩家双击安装；老玩家从托盘退出桌宠，下载并运行同一个文件，即可升级。安装后的入口放在开始菜单。每次需要下载整个程序，换来的是只维护一种下载包，玩家也不用挑选补丁。

## 1. 为什么选这个安装包

你提到的方式通常叫**自解压包（SFX）**，WinRAR、WinZip 一类工具可以把压缩内容封装成双击即可运行的 EXE。对这款桌宠，选择的关键是第二次安装时，旧快捷方式、登录启动和存档会发生什么。

| 方式 | 玩家得到什么 | 对本项目的代价 |
| --- | --- | --- |
| WinZip 等自解压 EXE | 双击即可释放文件，也可在解压后运行自带的安装程序。 | 只配置解压时，新旧程序可能留在两个目录。要统一开始菜单、卸载入口和更新行为，还要额外维护安装逻辑。[WinZip 自解压说明](https://www.winzip.com/en/product/self-extractor/) |
| NSIS 安装包 | 可定制安装向导、安装位置、快捷方式和卸载步骤。 | 适合需要自选目录、组件等安装选项的项目。桌宠当前只需要一次点击安装，引入另一套打包配置增加了维护工作。[NSIS 官方介绍](https://nsis.sourceforge.io/Main_Page) |
| **Squirrel.Windows 完整安装包** | 为当前 Windows 用户安装，正常情况下无需管理员权限。通过安装事件维护快捷方式，支持 Windows 卸载入口。 | 现有 Electron Forge 已配置，并生成过 v1.0.0 安装器。主要工作是完善安装事件、固定图标和验证旧版迁移，最符合本项目。[Forge 安装包说明](https://www.electronforge.io/config/makers/squirrel.windows) |

当前应用版本是 `1.0.1`。已有记录验收的是 ZIP；历史目录里的 v1.0.0 Setup 可用于开发对照。v1.0.2 的正式交付标准是下文的**安装版验收**。[v1.0.1 验收记录](v1.0.1-验收记录.md)

## 2. 安装包图标与实施改动

1. **使用指定的 logo。** 本机原稿是 `picture/lop.png`，与 `picture/软件图标/nagisa.png` 文件内容完全一致，均为 1254 × 1254。将原稿导出为多尺寸 ICO，至少包含 16、32、48、256 像素，使用仓库中的 [app-icon.ico](../nagisa-app/src/assets/app-icon.ico) 作为最终构建输入。若现有 ICO 预览与原稿一致，可直接复用。`picture/` 仅保存在本机，打包必须能在仅含仓库文件的环境下完成。新增美术需求为零。
2. **让 Windows 只生成需要的安装目标。** 在 [forge.config.ts](../nagisa-app/forge.config.ts) 保留 `MakerSquirrel`，其 `setupIcon` 已指向上述 ICO，`packagerConfig.icon` 负责应用 EXE。把 `MakerZIP` 的平台列表从 `['darwin', 'win32']` 改成 `['darwin']`。建议公开附件命名为 `Nagisa-Desktop-Pet-1.0.2-win-x64-Setup.exe`，后续只替换版本号。
3. **安装、升级和卸载时处理系统事件。** 在 [主进程入口](../nagisa-app/src/index.ts) 获取单实例锁及创建窗口之前接入 Forge 推荐的 `electron-squirrel-startup`，将它列为运行依赖。安装与更新时创建或刷新快捷方式，卸载时移除快捷方式。处理完维护事件直接结束该次启动；用户首次从安装器或开始菜单正常启动时，再打开桌宠和引导。验收时留意是否额外弹出第二只渚或手账。[Forge 启动事件说明](https://www.electronforge.io/config/makers/squirrel.windows#handling-startup-events)
4. **保住存档和登录启动。** 沿用 `nagisa-app`、`Nagisa Desktop Pet`、Squirrel 包标识以及现有 `app.getPath('userData')`。升级只替换程序文件，卸载处理也保留养成数据。现有[登录启动代码](../nagisa-app/src/settings-controller.ts)登记的是当前 `process.execPath`，安装后该路径可能含版本号。安装版应登记经实测可启动最新版本的稳定入口，例如安装根目录的应用启动器；便携版保留原逻辑。迁移时识别本项目已有的登录启动项，按原启用状态更新目标，避免同时启动旧便携版或已被替换的版本。收到卸载事件时，在结束维护进程前清理本应用登记的登录启动项。

## 3. 更新包怎么做，能不能跳版本

**本方案的“更新包”就是目标版本的完整安装包。** 它包含该版本运行需要的程序和资源。每次用目标版本源码重新构建一次，无需为每个旧版另外做包。跳版本有两个前提：安装身份一致，且目标程序能读取或逐步迁移旧存档。以后若修改存档格式，须保留从受支持旧格式迁到最新格式的完整路径。

| 玩家从哪里来 | 怎么更新 | 支持范围怎样确认 |
| --- | --- | --- |
| v1.0.0 或 v1.0.1 便携 ZIP | 用同一 Windows 账户，从托盘选择「退出」，直接运行 v1.0.2 Setup，再从开始菜单启动。确认进度后可以收起旧解压目录。想额外备份，可先在「设置 → 存档与隐私」导出。 | 这是首次安装程序、沿用原用户数据。分别用两个旧版创建的存档验证，玩家无需先装 v1.0.1。 |
| 已安装 v1.0.2，将来要升到 v1.0.4 | 退出桌宠，直接运行 v1.0.4 的完整 Setup。中间的 v1.0.3 可以跳过。 | v1.0.4 是示例。发布目标版时，用 v1.0.2 的实际安装和存档验证此路径，再列入当版支持记录。 |
| 将来希望只下载改动部分 | 可以另行接入 Squirrel 更新源。Forge 生成的 `RELEASES` 是更新索引，`*-full.nupkg` 是完整更新载荷；增量 `*-delta.nupkg` 由特定前版和目标版计算。 | 单个增量包依赖匹配的起点。跳版需要完整的增量链或可回退的目标版全量包。当前采用手动运行 Setup，玩家下载页只需提供 EXE。[Forge 产物说明](https://www.electronforge.io/config/makers/squirrel.windows) · [Squirrel 差分包原理](https://github.com/Squirrel/Squirrel.Windows/blob/develop/docs/using/delta-packages.md) |

## 4. 每次更新的固定流程

1. **先读上一版记录。** 打开[持续更新记录](更新记录.md)，确认最近一次发布的版本、公开附件和已测升级起点。本次变更在顶部建一个草稿条目，写下玩家会感受到的变化，以及是否涉及存档、安装身份或登录启动。
2. **构建新版本。** 从仓库根目录进入 `nagisa-app`。首次切换安装事件处理方式时安装运行依赖 `electron-squirrel-startup` 并提交锁文件。执行下列命令，同步应用与锁文件版本并构建安装包。后续版本把第一行的版本号替换成目标版本。

   ```powershell
   npm.cmd version 1.0.2 --no-git-tag-version
   npm.cmd ci
   npm.cmd run typecheck
   npm.cmd run make -- --platform=win32 --arch=x64
   ```

3. **取包、验包。** 在 `nagisa-app/out/make/squirrel.windows/x64/` 选取本次版本的完整 Setup EXE。该目录可能保留旧包，需核对版本号。将本次 EXE 按公开附件名整理到发布暂存目录，按第 5 节验收，使用 PowerShell 的 `Get-FileHash -Algorithm SHA256` 记录最终发布文件的哈希，同时记录字节数。
4. **发布到 GitHub。** 用对应源码提交建立 `v1.0.2` 标签和 Release 草稿，上传验收过的 EXE。说明中列出新增内容、旧 ZIP 用户迁移方法、实测升级范围及 SHA-256。同步修改 README 的下载文字和首次启动步骤。历史 Release 保留原附件；GitHub 自动生成的源码压缩包可照常显示。公开后从发布页核对版本、附件链接、大小与哈希。
5. **发布后回填同一个 Markdown。** 在[持续更新记录](更新记录.md)中将本版状态改为「已发布」，补全日期、构建提交、下载链接、验证结果和留给下版的事项，提交文档。新版本写在最上面，旧记录保留。下次制作安装包时从这份文件继续，避免凭记忆判断上次支持了哪些升级路径。

## 5. v1.0.2 验收

使用单独的 Windows 测试账户或虚拟机快照。升级前记下团子币、好感、已购玩具、角色位置、缩放和登录启动状态，便于升级后逐项核对。

| 用例 | 操作与通过标准 |
| --- | --- |
| 首次安装及图标 | 在无桌宠、无 Node.js 的普通 Windows x64 用户下离线运行已下载的 Setup。安装器在资源管理器显示指定 logo；开始菜单可启动桌宠，桌面只出现一只渚，托盘和手账可用，系统「已安装的应用」中有一个对应条目。 |
| 旧便携版迁移、跳版 | 用独立测试档分别执行 v1.0.0 ZIP → v1.0.2 Setup、v1.0.1 ZIP → v1.0.2 Setup。用默认用户数据路径，从开始菜单启动并确认实际版本、养成、偏好及位置。把旧解压目录移走后，开始菜单仍可启动新版。 |
| 安装版覆盖与登录启动 | 在隔离环境使用相同包标识的较低版本完整安装器作为起点，再运行 v1.0.2 Setup。核对开始菜单只指向新版、卸载列表只有一个应用、存档能读。分别验证开机启动原先开启和关闭两种情况，重新登录后分别只启动新版一次或保持关闭。注明测试起点是内部安装包还是已发布安装版。 |
| 卸载、重装和发放 | 通过 Windows 设置卸载，确认程序快捷方式及本项目的登录启动项被清理；重装后仍能读取测试存档。对照 Release 草稿中的附件名、字节数、SHA-256 和更新记录，四处版本号（应用、附件、标签、记录）一致。 |

以上为 v1.0.2 的实施与验收目标。实际通过的路径和未覆盖的项目在发布时填入[持续更新记录](更新记录.md)。
