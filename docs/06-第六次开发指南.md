**本次完成线**：从手账开始「温习功课」，看渚低头翻笔记。完成三次后，学习点从 0 依次变为 3、6、9，手账开放「朗读排练」和「整理戏剧部道具」。重启后能继续积累学习点；跨过 20 点时，解锁一条可以再次查看的专属待机语句。

接续[第五次开发指南](05-第五次开发指南.md)。现有工程已经有 v3 存档、活动倒计时、离线结算、三种零食和应急补给。总方案把学习、游戏和关系放在同一阶段；这份指南先完成学习与它直接解锁的两项活动，下一次再接猜团子小游戏。学习点达到 9 即可排练；好感达到 80 后的「听她练一句台词」是后续的独立互动。

## 2. 三项活动与两次解锁

学习点为永久累计值，初始 0。解锁后不会扣点。下表中的精力在开始时扣，收益只在到期后发放；取消沿用现有规则，已花精力保留，奖励为零。

| 活动 ID | 解锁及门槛 | 正式时长 | 完成收益 |
|---|---|---:|---|
| `study` 温习功课 | 空闲、精力 ≥8 | 3 分钟 | 学习点 +3，好感最多 +1 |
| `rehearse` 朗读排练 | 学习点 ≥9、空闲、精力 ≥12 | 5 分钟 | 学习点 +5，心情 +2，好感最多 +2 |
| `work_props` 整理戏剧部道具 | 学习点 ≥9、空闲、饱食 ≥15、精力 ≥16 | 6 分钟 | 团子币 +32，心情 −3，好感最多 +2 |

**进度显示**：6 点时显示「再得 3 学习点，开放戏剧部活动」；9 点起显示离 20 点还差多少；达到 20 点后展示已解锁的原创语句，例如“今天的台词，我已经能抬起头念给你听了。”一次排练可能从 19 到 24，判断应使用“旧值小于门槛且新值达到或超过门槛”。

## 3. 先把 v3 存档安全升级到 v4

在 [care.ts](../nagisa-app/src/care.ts) 给当前 `Care` 和 `Reward` 增加 `studyPoints: number`，并把 `careVersion` 升为 4。存档里的 `Care.studyPoints` 表示累计值，活动奖励和历史中的同名字段只表示本次增加量。新档三处都从适当的初始值开始：累计 0，旧活动奖励 0，取消记录实际获得 0。

在 [care-store.ts](../nagisa-app/src/care-store.ts) 按版本读取。**先固定旧版类型再改当前类型**，因为现有 v2 与当前版本共享 `ActivityFields`，直接给共享的奖励结构加必填字段会使旧记录无法通过校验。

1. 保留旧格式的四项奖励和 `rest/bakery` 两种 ID 的校验。为 v3 保留完整三种库存，v1/v2 继续走已有的食物补键逻辑。先读出合法的旧状态，再归一为 v4。
2. 迁移时复制币数、精力、三种库存、修订号、当日好感和在线时间；新增累计学习点 0。对正在进行的活动复制 ID、开始/到期时间和原奖励，在奖励对象补 `studyPoints: 0`。逐条复制历史并给 `entry.actual` 补 0。不能重建活动实例或重发开工奖励。
3. v4 要求学习点为非负安全整数；活动、完成和取消记录都带有效学习点收益，活动 ID 在五种允许值中。让主档与备份共用同一迁移函数，沿用已有的旧档备份、临时文件替换、更新版本保护。
4. 这次两个解锁都能由累计点数推导。持久资格由 `studyPoints >= 9/20` 判断；一次性提示在新奖励提交成功时依据跨线产生。离线跨线时，新资格和语句在手账可见。保留原有启动结算不弹历史气泡的行为，避免重启重复庆祝。

**检查点**：用第五次开发的测试档（已有红豆面包、正在帮工）升级。小面包等库存、余额和活动 ID 均应相同，学习点显示 0，到期后仍只得到一次原工资。

## 4. 扩展原活动引擎

**规则与门槛。** 在 `care.ts` 扩展 `ActivityKind`、`isActivityKind()` 和 `activityRules`。给所有规则统一加解锁门槛 `minStudy`，给休息和面包店的奖励补 0 点。三个新增规则可按以下内容追加到规则表：

```ts
study: { label: '温习功课', durationMs: 180_000, cost: 8, minFullness: 0, minStudy: 0,
  reward: { coins: 0, energy: 0, mood: 0, affection: 1, studyPoints: 3 } },
rehearse: { label: '朗读排练', durationMs: 300_000, cost: 12, minFullness: 0, minStudy: 9,
  reward: { coins: 0, energy: 0, mood: 2, affection: 2, studyPoints: 5 } },
work_props: { label: '整理戏剧部道具', durationMs: 360_000, cost: 16, minFullness: 15, minStudy: 9,
  reward: { coins: 32, energy: 0, mood: -3, affection: 2, studyPoints: 0 } },
```

在 `activityUnavailable()` 加入学习点检查，让手账和主进程调用同一规则。现有 `startActivity()` 已处理修订号、互斥、精力扣除和奖励快照；继续传活动 ID 启动即可。现有 [preload](../nagisa-app/src/preload.ts) 和主进程的启动 IPC 共用 `ActivityKind`，无须给学习单开一条扣精力通道。

**计时与结算。** 在 [care-runtime.ts](../nagisa-app/src/care-runtime.ts) 将 `durations` 扩展至五项：正式时长从规则表取，现有快速模式统一返回 10 秒。[renderer.ts](../nagisa-app/src/renderer.ts) 的读取失败分支也有一份仅含休息和面包店的时长对象，要同步更新。建议让这两个地方共用一个生成时长表的函数，并显式返回 `ActivityDurations`。

- `finishDue()` 用**该活动存档中的奖励快照**累加学习点，夹到非负安全整数范围，把实际增量写入 `entry.actual.studyPoints`。好感沿用原有日限和总上限；今天好感已满不影响学习点与工资。
- `cancelActivity()` 的零收益对象补上学习点 0。玩家在 6 点取消第三次温习，学习点仍是 6，戏剧部仍锁定。
- 学习点、最近记录、清除活动一起走原有提交。存档写入成功后才向窗口发布；磁盘失败时保留活动并沿用运行时重试。无需让手账根据倒计时自行发奖。

## 5. 接入手账、角色和解锁反馈

| 修改位置 | 具体实施 | 完成时检查 |
|---|---|---|
| [activity-panel.ts](../nagisa-app/src/activity-panel.ts) | 给已有 `activityOption()` 加三行入口。未到 9 点的两项保留可见，禁用按钮并写明还差几点。给 `rewards()` 增加学习点，最近记录显示实际增量。现有取消提示只区分面包店与休息，改为按活动名、实际启动消耗与收益说明 | 取消温习时提示“已消耗 8 精力，本次不获得学习点”；整理道具显示工资，温习显示点数 |
| `renderer.ts / Journal()` | 在概览加「学习点」，活动区显示下一次解锁进度；达到 20 点可在手账查看语句。店铺与背包继续复用现有组件，活动期间可购物、暂停喂食 | 离线完成第三次温习后，打开手账即可开始排练 |
| `renderer.ts / Pet()` | 给五种活动建完整的 `Record<ActivityKind, readonly Frame[]>`；替换 `restorePose()` 里的二选一。静态导入三组图片，按第 1 节时长循环播放 | 温习时翻页，排练时念台词，整理时出现道具箱。轻点问候后回到原活动 |
| `Pet().updateCare()` | 用已提交的 `completed` 产生反馈，沿用活动实例 ID 去重。结算后的总点数减去本条实际增加量就是跨线前的点数；达到门槛时在同一条完成气泡中提示解锁。普通学习完成可说“这一页记好了，学习点 +3”。面包店保留递纸袋动画，道具整理使用自己的收手帧 | 刷新快照或重新打开手账不会重复弹气泡；隐藏状态下结算也能留下记录 |

20 点的台词建议在空闲状态下由玩家轻点渚时展示一次，再与原问候轮换，同时保留手账中的查看入口。这样玩家可以主动验证，不必一直等待随机气泡。角色加载旧快照时沿用现有的修订号检查。

## 6. 试玩与验收

在项目根目录启动一个独立测试档。快速模式只改活动时长，数值、门槛和离线结算规则与正式模式相同。

```powershell
Set-Location '.\nagisa-app'
$env:NAGISA_TEST_DATA = Join-Path $env:TEMP ('nagisa-study-' + [guid]::NewGuid().ToString('N'))
$env:NAGISA_FAST_ACTIVITY = '1'
npm.cmd run typecheck
npm.cmd start
```

重启复测时继续使用同一终端和测试目录。下表标明“新档”的用例以饱食 55、精力 70、好感 0、学习点 0 开始，数值在快速模式下连续操作，避免混入空闲恢复。

| 验收项 | 怎么操作 | 通过标准 |
|---|---|---|
| 三次温习 | 新档连续完成三次，各活动之间立即接下一次 | 学习点 0 → 3 → 6 → 9；精力 70 → 62 → 54 → 46；好感升到 3。前两次无法排练，第三次同时开放排练与整理道具 |
| 实际排练 | 从 9 点、46 精力、60 心情开始排练一次 | 启动扣 12 精力，到期学习点 14、精力 34、心情 62；若当日上限未触及，好感再增 2 |
| 跨过 20 | 从 14 点连续完成两次排练 | 学习点 14 → 19 → 24；第二次完成解锁台词。重启后仍可查看，首次解锁提示不会重播 |
| 整理道具 | 单独从 9 学习点、46 精力、30 币、心情 60 开始 | 开工时精力 30；到期余额 62、心情 57、学习点仍 9，好感最多 +2。另测饱食 14 或精力 15，均不能开工 |
| 取消与互斥 | 6 点时开始温习，先尝试另一项活动，再确认取消；重新开始并完成 | 不能同时排练或帮工；取消没有学习点、已扣精力保留。重开只结算最后完成的那一次 |
| 离线与重复结算 | 第三次温习开始后退出，超过截止时间再启动两次 | 两次启动读到的都是 9 点；手账只有一条对应实例的完成记录，无需点击领取 |
| 好感日限与写盘失败 | 用当日已获 12 好感的测试档完成温习；另用第四次指南中的临时文件冲突方法阻止一次到期写入 | 前者学习点仍 +3，好感不变；后者不提前解锁，恢复可写后只增加一次 |
| 旧档与回归 | 分别从合法 v1/v2/v3 档升级，另测 v3 主档损坏、可用备份恢复；帮工和喂食各做一次 | 保留旧库存、在线余数及旧活动原奖励（旧版本欠缺的字段补默认值）；小面包、商店、休息和帮工仍可用 |
| 正式时长与美术 | 退出程序，执行 `Remove-Item Env:NAGISA_FAST_ACTIVITY`，重启后分别查看三项活动并跑一次温习 | 三项正式时长为 3、5、6 分钟；温习结束只加 3 点。三组动作在浅色和深色桌面上都完整，隐藏再找回能恢复对应姿势 |

当「三次温习 → 开放戏剧部 → 完成一次排练 → 重启保留点数」全部可操作时，本次学习链路完成；已有排练帧还可供后续好感互动和台词接龙复用。
