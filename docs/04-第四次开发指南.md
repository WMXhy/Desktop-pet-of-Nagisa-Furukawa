## 3. 扩展存档，先让旧进度能正常打开

从 `nagisa-app` 运行 `npm.cmd run typecheck`。主要修改 [care.ts](../nagisa-app/src/care.ts) 和 [care-store.ts](../nagisa-app/src/care-store.ts)。把 `careVersion` 升至 2，保留现有字段。建议在 `care.ts` 增加以下类型：

```ts
export type ActivityKind = 'rest' | 'bakery';
export type Reward = { coins: number; energy: number; mood: number; affection: number };
export type Activity = {
  id: string;
  kind: ActivityKind;
  startedAt: number;
  endsAt: number;
  reward: Reward;
};
export type ActivityRecord = {
  id: string;
  kind: ActivityKind;
  outcome: 'completed' | 'cancelled';
  endedAt: number;
  actual: Reward;
};
```

- 在 `newCare()` 中加入 `activeActivity: null as Activity | null`、`activityLog: [] as ActivityRecord[]` 及 `online: { hungerMs: 0, idleMs: 0 }`。时间点用 UTC 毫秒，两个余数记录未满一档的在线毫秒数。活动历史保留最近 20 条，最近一条放最前。
- 当前 `validCare()` 按版本严格比较。把原有字段校验提取为共用函数，在 `readSave()` 分两条路：合法 v1 复制自己的币、库存、修订号等字段，只补新增默认值；v2 同时校验活动、记录与余数。主档和备份都走这个读取流程。首次保存迁移结果前保留有效旧档备份。高于 v2 的存档继续提示升级。
- 校验活动种类、非空实例 ID、整数时间点、`endsAt > startedAt`，奖励各项为合理范围内的整数（心情允许负值）。`hungerMs` 范围为 0～599999，`idleMs` 为 0～299999。奖励值存入活动实例，升级后也能按开工时的约定结算。
- **检查点**：用第三次开发喂过一次的 v1 存档副本启动，预期饱食 73、小面包 1、团子币 30，活动为空。重启后不能再次获得初始面包。

## 4. 用同一套函数做休息和帮工

先在 `care.ts` 写纯函数，传入当前状态与时间，返回候选结果；磁盘写入仍由 store 负责。规则表和活动实例可以这样建立：

```ts
const rules = {
  rest: { durationMs: 300_000, cost: 0, minFullness: 0,
    reward: { coins: 0, energy: 15, mood: 0, affection: 0 } },
  bakery: { durationMs: 180_000, cost: 10, minFullness: 15,
    reward: { coins: 18, energy: 0, mood: -3, affection: 1 } },
} satisfies Record<ActivityKind, {
  durationMs: number; cost: number; minFullness: number; reward: Reward;
}>;

function makeActivity(kind: ActivityKind, id: string, now: number, durationMs: number): Activity {
  return { id, kind, startedAt: now, endsAt: now + durationMs, reward: { ...rules[kind].reward } };
}

function remainingSeconds(activity: Activity, now: number) {
  return Math.max(0, Math.ceil((activity.endsAt - now) / 1000));
}
```

依次实现以下入口。每次真实提交只增加一次 `revision`；读取、重复结算以及验证失败均不增加。

| 入口 | 处理顺序 |
|---|---|
| `start(kind, revision, now)` | 先推进时间并处理已到期活动；校验传入修订号、种类、空闲、饱食和精力 → 主进程用 `randomUUID()` 分配实例 ID → 一次提交「扣精力 + 写入 activeActivity」。重复点击返回最新状态，现有活动不能被覆盖 |
| `finishDue(id, now)` | 读取当前活动；为空、ID 不同或 `now < endsAt` 就返回。否则计算奖励后的完整状态，把实际增减写入一条完成记录，清空活动，**同时写入同一份主档**。完成时间记 `endsAt`；离线归来的好感按本次实际结算的本地日期计入当日上限 |
| `cancel(id, revision, now)` | 先检查是否已到期，再核对当前 ID 和修订号。仍在进行才写入取消记录（实际收益全为 0）并清空活动。上一次活动留下的按钮或计时回调不能碰到下一次活动 |

把 `feedBread()` 中现有的好感日限逻辑提取为小函数，喂食与帮工共用。结算前后分别取数值，记录实际差额：精力从 98 恢复到 100，记录应写“精力 +2”。关掉手账、隐藏角色或中途退出都不等于取消活动。

在 store 内，把原先 `feed()` 中的「写备份 → 临时文件替换主档 → 更新内存」抽成一个共用提交函数。开工、取消、自然变化、到期奖励和喂食都走它。写入失败保留旧内存与原活动，提示重试；仅在提交成功后才广播新状态和动作。沿用已有的单实例锁。

## 5. 主进程管时间，两个窗口负责显示

在 [index.ts](../nagisa-app/src/index.ts) 的 `startPet()` 创建 store 后接入调度。这里有两种时间，分别验证：

1. **真实到期时间。** 活动一旦开始就保存 `endsAt`。启动读取存档、系统唤醒、玩家读取/操作活动以及定时器到点时，都调用同一个 `finishDue`。每次成功提交后重新安排唯一的超时回调，回调携带当时的实例 ID。到期前退出、到期后再开都只完成原来的那一次。写盘失败时延迟重试并显示原因，避免以零延时循环写盘。
2. **实际在线时间。** 每次启动建立新的内存采样起点，定期用单调时钟取得本段经过的毫秒数。以整数除法求跨过多少个 10 分钟或 5 分钟阈值，用余数保留下次继续累计。在开工、取消和结算前先结清上一段；若一次采样跨越到期点，把这段拆成「到期前忙碌」与「到期后空闲」。监听 `powerMonitor` 的 `suspend` 和 `resume`：挂起前保存在线余数，恢复时重建采样起点，再按真实时间检查活动。正常退出前也保存余数，启动时从保存的余数接着算。隐藏窗口期间应用仍在线。
3. **避免频繁写盘。** 手账每秒用 `remainingSeconds` 刷新文字，倒计时到 0 时显示“正在结算”，等主进程回执。内存中的在线余数在玩家操作、跨越自然变化阈值、休眠和退出时一起提交；没有数值变化的每秒刷新不写 JSON。失败重试要沿用上一次成功提交的位置，避免同一段在线时间被计算两次。

**接好窗口通信**：在 [preload.ts](../nagisa-app/src/preload.ts) 和 [pet-api.d.ts](../nagisa-app/src/pet-api.d.ts) 增加 `startActivity(kind, revision)`、`cancelActivity(id, revision)` 与 `onCareChanged(callback)`（返回取消订阅函数）。在 `openJournal()` 中沿用 `journalContents.ipc.handle` 和 `senderFrame === mainFrame` 校验，仅接受已知活动及有效参数。主进程在成功提交后把带 `revision` 的快照发送给角色和已打开的手账。角色窗口也要注册只读状态查询，首次加载或重新显示时能恢复进行中的动作。

在 [renderer.ts](../nagisa-app/src/renderer.ts) 的 `Journal()` 先订阅再读初始快照，忽略晚到的旧修订号。保留状态和背包，追加以下三种可见内容：

- **空闲时**显示「休息 5 分钟」「面包店帮工 3 分钟」，按钮旁写出消耗、收益与实际可恢复精力。体力或饱食不足要指出是哪一项不足。
- **进行中**显示活动名、剩余分秒、预计结果和「取消活动」。取消前确认，取消确认框停留期间计时继续。沿用现有请求锁，等主进程回执后再允许下一次点击。
- **完成或取消后**在最近记录里显示时间及实际结果。例如“面包店帮工完成，团子币 +18，心情 −3，好感 +1”。关闭手账后仍可查到这一条。

**动画接入**：当前 `Pet()` 的一次性 `play()` 播完会调用 `idle()`。把结束后的选择改为「根据最新快照恢复姿势」：空闲 → 原有眨眼，休息 → 两帧缓慢往返，帮工 → 四帧间歇循环。新的完成事件抢占循环，只播一次两帧递袋动作；用实例 ID 区分新事件和历史记录。普通状态刷新不重启动画，问候完再回当前活动。隐藏时暂停动画，找回时按最新状态恢复。离线完成的收入在手账可见，无需重播历史动作。

## 6. 开发时用 10 秒验证，最后恢复正式时长

先用独立测试存档，保留自己的养成进度。现有程序使用 `app.getPath('userData')`；若用环境变量切换目录，需先在入口接入：限开发模式，在申请单实例锁前创建指定的测试目录，再调用 `app.setPath('userData', 该绝对路径)`。另外在主进程取时长时，仅当 `!app.isPackaged` 且 `NAGISA_FAST_ACTIVITY === '1'` 时把**新开活动**时长改为 10 秒。测试开关只改变活动时长，自然变化阈值仍按原值。手账从实际时长配置生成说明。

```powershell
# 从 nagisa-app 运行；先实现上段的两个开发开关
$env:NAGISA_TEST_DATA = Join-Path $env:TEMP ('nagisa-activity-' + [guid]::NewGuid().ToString('N'))
$env:NAGISA_FAST_ACTIVITY = '1'
npm.cmd run typecheck
npm.cmd start
```

退出重开时沿用同一终端和同一测试目录，仅重新执行 `npm.cmd start`。下表的数值用例各从独立的新档或指定夹具开始。要测正式时长，先结清已有的测试活动，移除本终端的 `NAGISA_FAST_ACTIVITY` 环境变量再重启。

| 用例 | 操作 | 通过标准 |
|---|---|---|
| 在线完成第一次帮工 | 新档 30 币、70 精力、60 心情；开工后等 10 秒 | 开工时 30 币、60 精力；完成后 48 币、60 精力、57 心情、好感 1，只有一条完成记录 |
| 离线归来与重复结算 | 开工 2 秒后从托盘退出；等到已过截止时间，重启两次，并反复开关手账 | 首次归来结算到 48 币；以后始终是 48。若到期前重启，应继续原倒计时 |
| 互斥、门槛与取消 | 连点开工，再尝试休息；到期前确认取消。分别用精力 9 或饱食 14 的测试档开工 | 只扣一次精力；取消后余额 30、精力 60、没有完成奖励。任一门槛不足均不能开工；取消确认框放到过期再确认应得到完成结果 |
| 主动休息 | 新档 70 精力开始休息；另用 98 精力重复一次 | 分别到 85 和 100，记录 +15 与 +2；余额不变 |
| 自然变化 | 构造在线余数距两个阈值各差 1 秒的测试档，空闲运行 1 秒；另在活动中跨过阈值 | 空闲时饱食 −1、精力 +2；活动期间只累计饱食时间，精力余数保留。关闭程序或系统休眠 10 分钟，不补扣离线饱食 |
| 兼容、上限与写入失败 | 用合法 v1 主档及备份升级；用当日好感已得 12 的档完成帮工；用第三次指南的临时文件冲突法阻止一次结算写入 | 旧币数和库存保留；好感不超限、工资正常；写入失败没有成功动画，恢复可写后只发一次工资 |
| 桌面回归 | 帮工中隐藏角色、重开手账、找回；完成后喂一个面包并拖动角色 | 找回时显示正确活动，完成后能正常喂食、拖动、眨眼；切换窗口不重开活动 |
| 正式时长 | 关闭快速模式，完整跑一次帮工与休息 | 新活动分别显示约 3:00、5:00；自然变化、截止时间与界面一致。满 5 分钟主动休息只获得休息奖励，期间不叠加空闲恢复 |

**交付时可用一句话验收**：渚记得出门时扣过的精力，也记得回家时领过的工资。确认从开工到重启都只有一条结算记录，再进入下一次的零食商店开发。
