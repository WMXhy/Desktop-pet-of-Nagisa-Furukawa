## 2. 一次状态变更如何到达磁盘与窗口

以买面包为例：手账提交商品 ID、数量、当前修订号 → [preload](../nagisa-app/src/preload.ts) 暴露具体方法 → 主进程核对消息来源 → [运行时](../nagisa-app/src/care-runtime.ts) 先结清已经到期的活动 → 规则函数检查余额与库存 → [存储层](../nagisa-app/src/care-store.ts) 备份旧状态、原子替换主档、更新修订号 → 已打开的窗口通过[快照订阅](../nagisa-app/src/care-snapshot.ts)刷新。失败或旧修订号走已有错误路径。购买、活动、游戏、关系的改动沿用该入口可以避免多扣或重复发奖。

- **落盘文件**：`app.getPath('userData')` 下的 `save.json`、`save.backup.json` 和 `pet-position.json`。v6 读档含 v1～v5 迁移；v6 关系记录包含唯一里程碑、达成时间或旧档继承标记。设备偏好设置文件仍待实现。
- **时间约定**：定时活动保存截止时刻及启动时约定的奖励；运行时负责在线余数、休眠与恢复。小游戏不会因为离线而自动发奖。每日好感边界用本机自然日。
- **界面边界**：Electron 主进程负责系统状态、存档与窗口，React 渲染角色、手账、游戏。刷新可见数据不触发收益。小游戏、手账、角色的 IPC 按各自窗口注册，扩展接口同时更新 [窗口类型声明](../nagisa-app/src/pet-api.d.ts)。
- **开发环境**：本次本机依赖为 Electron 45.4.1、React 19.3.1、TypeScript 5.9.3、Electron Forge 7.11.2。重新搭建环境使用 `nagisa-app/package-lock.json` 和 `npm.cmd ci`。

## 4. 已知交付差距与后续变更入口

- **设置与系统行为**：托盘目前有打开手账、隐藏、穿透、找回和退出。角色尺寸当前固定为 256；独立设置窗口、预览与撤销、登录启动、快捷键、声音/动画选项、安静时段与全屏免打扰仍属于最终开发任务。
- **日常入口与存档管理**：总方案中的角色右键菜单、可跳过的首次引导，以及给玩家操作的导入、导出、恢复和清空入口尚待补齐。现有损坏主档自动回退与用户主动恢复是两种不同的使用场景。
- **发布**：先把 Windows ZIP 配置和候选包复测跑通，再决定分发哪一份产物。源码版本、养成存档版本和偏好文件版本分别记录。
- **范围决定**：首个完整版本以 Windows 本地玩法和长期使用为目标。是否添加 API Agent 由项目作者以后决定。后续优化可以从真实试玩、性能测量和用户反馈开始立项。
