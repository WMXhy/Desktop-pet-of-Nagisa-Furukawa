## 2. 定商品表，先让一笔购买可以独立验证

在 [care.ts](../nagisa-app/src/care.ts) 定义食物 ID、单价与使用效果，供主进程校验和手账预览共用。素材导入留在渲染侧。三种食品按数量叠放，购买增加库存，实际喂给渚时才增加状态值。

| ID | 商品 | 单价 | 每份食用效果 |
|---|---|---:|---|
| `bread` | 小面包 | 6 币 | 饱食 +18，好感 +1 |
| `redBeanBread` | 红豆面包 | 12 币 | 饱食 +24，心情 +3，好感 +2 |
| `dangoSnack` | 团子点心 | 10 币 | 饱食 +12，心情 +6，好感 +2 |

把下列示例放在同一模块。它使用下一节的三种食品库存类型，保留现有 `CareResult` 返回形式。现有流程由存储层提交时更新修订号，购买函数只计算下一份状态。

```ts
export const foods = {
  bread: { name: '小面包', price: 6, fullness: 18, mood: 0, affection: 1 },
  redBeanBread: { name: '红豆面包', price: 12, fullness: 24, mood: 3, affection: 2 },
  dangoSnack: { name: '团子点心', price: 10, fullness: 12, mood: 6, affection: 2 },
} as const;
export type FoodId = keyof typeof foods;

export function isFoodId(value: unknown): value is FoodId {
  return typeof value === 'string' && Object.prototype.hasOwnProperty.call(foods, value);
}

export function buyFood(state: Care, id: FoodId, qty: number, revision: number): CareResult {
  if (revision !== state.revision) return { ok: false, state, message: '余额或库存已更新，请重新确认。' };
  if (!Number.isSafeInteger(qty) || qty < 1) return { ok: false, state, message: '请输入正整数数量。' };
  const total = foods[id].price * qty;
  if (!Number.isSafeInteger(total) || total > state.coins)
    return { ok: false, state, message: '团子币不足。' };
  const count = state.inventory[id] + qty;
  if (!Number.isSafeInteger(count)) return { ok: false, state, message: '库存已达到上限。' };
  return { ok: true, state: { ...state, coins: state.coins - total,
    inventory: { ...state.inventory, [id]: count } } };
}
```

**应急补给**：增加 `canClaimBread(state)`，同时检查三个条件：所有食品库存都是 0、饱食 **<15**、余额 **<6**。领取命令先核对修订号，再重新判断资格，一次只加 1 个小面包，币数原样。可把同一条件用于决定是否显示「领取应急小面包」。领到后背包已有食物，自然失去资格，无需新增每日领取字段。

## 3. 保住旧档里的面包和正在进行的帮工

新档使用 `inventory: { bread: 2, redBeanBread: 0, dangoSnack: 0 }`。建议把存档升级到 v3；此处要特别留意，当前代码的 `CareV1` 和 `Care` 共用 `initialCareFields()` 推导的库存类型。改新版库存前，先把旧版的 `{ bread: number }` 固定成显式类型，再为当前 `Care` 使用 `Record<FoodId, number>`。

在 [care-store.ts](../nagisa-app/src/care-store.ts) 更新 `readSave()`、校验函数及旧档备份类型：

1. **v1** 用旧字段校验，沿用原迁移逻辑补齐空活动、历史和在线余数，再补两个新库存键。已有 `bread` 数量即使为 0 也保留。
2. **v2** 用原 `validV2Fields()` 检查活动和在线计时。迁移时复制全部字段，只替换版本和库存结构。特别保留 `activeActivity.id`、`endsAt`、已约定奖励、`activityLog`、`daily`、`online` 与 `revision`；现有 `upgradeCare()` 会把活动设为空，不能直接用于正在帮工的 v2 档。
3. **v3** 校验三种库存均为非负安全整数；缺键的 v3 档走现有备份恢复流程。主档和备份都经同一版本分支读取；升级时先保存旧档原文对应的数据，再原子替换主档。未知更高版本继续提示升级。

**检查点**：从独立的 v2 测试档开始，里面只有 1 个小面包且有一份进行中的工作。首次升到 v3 后库存应为 `1/0/0`，原活动继续按原截止时间结算；第二次启动不再迁移，也不补发工资。

## 4. 接入主进程、手账和角色窗口

| 位置 | 具体改动 |
|---|---|
| [care.ts](../nagisa-app/src/care.ts) | 增加购买和应急补给纯函数，把喂食推广为 `feedFood(state, id, revision, day)`。复用 `gainAffection()`，饱食和心情上限均为 100；无库存、饱食已满、活动进行中仍拒绝喂食。现有 `feedBread` 可委托给 `feedFood(..., 'bread', ...)`，方便分步接入。 |
| [care-runtime.ts](../nagisa-app/src/care-runtime.ts) | 给现有返回对象增加 `buy`、`claimBread`、按 ID 喂食三个入口，均走 `apply()`。例如 `buy: (id, qty, rev) => apply(s => buyFood(s, id, qty, rev))`（参数按上面的类型声明）。这样购物前会先结清到期工资，余额与库存同一次写入，提交成功才发布快照。 |
| [index.ts](../nagisa-app/src/index.ts) | 在手账的 `journalContents.ipc` 上注册 `care:buy`、`care:claim-bread` 和带食品 ID 的喂食入口。沿用现有 `senderFrame` 校验，拒绝未知 ID、非法数量与修订号；主进程自行计算价格。保留原 `care:feed` 的小面包语义直至旧调用切换完成。 |
| [preload.ts](../nagisa-app/src/preload.ts) 与 [pet-api.d.ts](../nagisa-app/src/pet-api.d.ts) | 为 `window.pet` 增加 `buyFood(id, qty, revision)`、`claimBread(revision)`、`feedFood(id, revision)`，都返回 `Promise<CareResponse>`。让 `onFed(callback)` 将成功吃掉的食品 ID 传给回调，同时保留取消订阅函数。 |
| [renderer.ts](../nagisa-app/src/renderer.ts) | 在 `Journal()` 中复用现有 `submit()`、请求锁和快照订阅；`Pet()` 按 `care:fed` 通知里的 ID 选择进食帧。购买成功只更新状态，喂食成功才发动作通知。 |

**旧档、离线结算和重复点击有一个共同测试点**：当工作刚好到期，`apply()` 可能先结算并推进修订号。若购买提交的是旧修订号，返回最新状态，提示重新确认数量及总价。玩家确认后再买一次。购买写盘失败时沿用旧币数和库存；沿用的错误提示要适用于购物，例如“存档写入失败，本次购买未完成”。

## 5. 玩家在手账里怎么操作

1. 在现有手账加「零食店」入口，打开时能看到可用余额。每行显示图标、名称、单价、食用效果、数量、总价和购买按钮。数量初始为 1，可增加或减少；数量不合法或余额不足时显示原因。
2. 例如余额 48，选 2 个小面包，按钮显示「花 12 币购买」，旁边显示「购买后剩 36 币」。提交后留在商店，看到“小面包 ×2 已放入背包”。在成功结果旁提供「现在喂给她」，按**最新快照的修订号**喂 1 个对应食品。购买与喂食是两次独立提交，关闭页面不会丢失买到的食物。
3. 背包用同一份商品表渲染，按品种堆叠，保留现有小面包入口。选中食品时预览实际变化，例如饱食 95 吃红豆面包显示“95 → 100”；好感接近每日上限时只显示实际可增加的点数。
4. 活动期间允许购物。已购买食品保留在背包，「现在喂给她」显示“活动结束后可喂食”。手账的忙碌锁沿用到提交结束；`onCareChanged` 继续根据修订号忽略过期回包。
5. 在渲染侧建立食品 ID 到图标和帧数组的映射，两种新食品都以现有 `eat4` 收尾。为每种食品提供对应的简短反馈，例如“这个红豆馅好甜。”角色隐藏时交易和喂食照常保存，重新显示时沿用现有待机逻辑。

## 6. 从新档完成一次正式试玩

在项目根目录打开 PowerShell。下面使用项目已有的独立测试目录开关，不影响日常存档。正式验收沿用活动规则里的 3 分钟；先移除上一轮测试可能留下的快速模式。

```powershell
Set-Location '.\nagisa-app'
$env:NAGISA_TEST_DATA = Join-Path $env:TEMP ('nagisa-shop-' + [guid]::NewGuid().ToString('N'))
Remove-Item Env:NAGISA_FAST_ACTIVITY -ErrorAction SilentlyContinue
npm.cmd run typecheck
npm.cmd start
```

重启复测时保持同一个终端和测试目录，只需重新运行 `npm.cmd start`。需要构造边界状态时，完整退出程序并修改独立测试档，或用内存中的 `newCare()` 构造输入。

| 用例 | 操作 | 通过标准 |
|---|---|---|
| 第一份工资 | 新档开工，完整经过 3 分钟，买 2 个小面包，再喂 1 个 | 币数 30 → 48 → 36；库存 2 → 4 → 3；若总在线时间不足 10 分钟，饱食 55 → 73。重启仍有 36 币和 3 个面包 |
| 买对、吃对 | 从新档各买 1 个红豆面包和团子点心，先后喂食 | 余额 30 → 18 → 8，两个新库存分别归零，小面包仍有 2 个；未跨自然衰减阈值时饱食 55 → 79 → 91，心情 60 → 63 → 69，好感 0 → 2 → 4；动画里的食物与点击的商品一致 |
| 余额与数量边界 | 余额恰为 6 时买 1 个小面包；余额 5 时再尝试。另测 0、负数、小数、过大数量和未知商品 ID | 第一笔成功，余额可为 0；其余均被拒绝，库存和币数不变 |
| 重复购买与写盘失败 | 对同一修订号提交两笔相同请求；另在测试目录制造一次主档临时文件写入失败 | 同一修订号只成交一次；写盘失败时不会出现“已购买”，重开后无少币或多货 |
| 应急补给 | 设饱食 14、余额 5、三种库存全 0，领取后立即再次领取 | 第一次免费得到 1 个小面包，第二次拒绝；另测饱食 15、余额 6 或仍有一个团子，任一条件成立都不能领取 |
| 忙碌时购物 | 开工期间买一份点心，尝试立即喂食；等完工后再喂 | 可以购买、当时无法喂食；工资只到账一次，完工后可用刚才买的同一份点心 |
| 旧存档和回归 | 分别从合法 v1、带未完活动的 v2 档启动；重开手账、隐藏和找回角色 | 旧库存、币数、位置与已有进度恢复，新食品初始为 0；原工作照常结算，原有眨眼、休息、帮工与小面包喂食可用 |

**试玩记录**：完成上述流程后，记下第一次找零食店时点了哪里，以及购买、完工、喂食的提示有没有重复或遮住角色。如果开店、确认总价、喂食这三步能连续做完，并且重启后账目一致，就达到了总方案阶段三的可试玩节点。
